# Artwork api for art galleries, built with NestJS and PostgreSQL

Repo: [github.com/Froggys974/Art-nest-project](https://github.com/Froggys974/Art-nest-project)

## Description

ConsignArt is an API for galleries to manage artists, artworks, exhibitions and sales. Galleries deposit artworks from artists, list them for sale, loan them to exhibitions, and record sales with an automatic commission split between the gallery and the artist. Roles are admin, gallery, artist and collector.

## Tech stack

- NestJS 11, TypeScript
- PostgreSQL 18, TypeORM
- JWT authentication (access and refresh tokens), role based guards
- Swagger for API documentation
- Docker Compose for local development

## Prerequisites

- Docker and Docker Compose
- Node.js 26 if you want to run commands outside Docker

## Setup

Copy the example env file and fill in real values.

```bash
cp .env.example .env
```

All variables are documented in `.env.example`. `JWT_SECRET` and `JWT_REFRESH_SECRET` need at least 16 characters. `ADMIN_PASSWORD` needs at least 8 characters. An admin account is seeded automatically on first boot with `ADMIN_USERNAME` and `ADMIN_PASSWORD`.

## Run with Docker

```bash
# start postgres, api and adminer
npm run docker:up

# run a command inside the api container
npm run docker -- <command>

# stop everything
npm run docker:down

# rebuild the api image and reset volumes
npm run docker:rebuild
```

The api container mounts `src` and `test`, so `start:dev` reloads on file changes. Adminer is available on `http://localhost:8080` to inspect the database. On first boot the app also seeds an admin account and a small demo dataset, see below.

## Database migrations

Outside production the app keeps `synchronize: true` in `src/app.module.ts`, like a normal NestJS project: the schema follows the entities automatically, so local iteration never needs a manual migration step. In production `synchronize` is always `false`, the deployed app never guesses the schema at boot.

Migrations still exist and are the only way the schema is created in production. They are driven by a small standalone connection in `src/data-source.ts`, used only by the TypeORM CLI (the Nest app itself never imports it). Migration files live in `src/migrations`, generated by comparing the entities in `src/**/*.entity.ts` against a real database, then reviewed and committed like any other code change.

```bash
# start postgres only
docker compose up -d postgres

# apply pending migrations (needed before the app can boot on an empty database)
npm run docker -- npm run migration:run

# start the rest of the stack
npm run docker:up
```

Common commands, all run inside the api container:

```bash
# generate a migration from entity changes
npm run docker -- npm run migration:generate -- src/migrations/AddSomeColumn

# create an empty migration to write by hand
npm run docker -- npm run migration:create -- src/migrations/CustomChange

# apply pending migrations
npm run docker -- npm run migration:run

# revert the last applied migration
npm run docker -- npm run migration:revert

# list applied and pending migrations
npm run docker -- npm run migration:show
```

After changing an entity, generate a migration against a database with no pending schema drift, read the generated SQL, then commit both the entity and the migration together. In production, run migrations as a separate deploy step before starting the app, with `npm run migration:run:prod` on the built `dist` output. This avoids two app instances racing to alter the schema at the same time.

## Demo data

On first boot in a non-production environment, `DemoSeedService` seeds a ready-to-use dataset alongside the admin account: a validated gallery, an artist linked to their own account, a collector, one available artwork, and a second artist already sitting at 49 active artworks to demo the 50-artwork cap. All demo accounts use the password `demo12345`.

| Username | Role |
| --- | --- |
| `demo_gallery` | gallery, already validated |
| `demo_artist` | artist, linked to the seeded artist profile |
| `demo_collector` | collector |

## Run tests

```bash
# unit tests
npm run test

# coverage
npm run test:cov

# integration tests (real HTTP requests through a real Postgres, run inside
# the api container since only it can reach DB_HOST=postgres)
npm run docker -- npm run test:e2e
```

## API documentation

Once the api is running, Swagger UI is available at `http://localhost:3000/api/docs`. All routes are versioned under `/api/v1`.

## Health check

`GET /api/v1/health` checks the database connection and is used by the Docker healthcheck.
